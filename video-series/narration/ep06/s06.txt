There's an old joke in programming that there are only two hard things: cache invalidation, and naming things. Content addressing is a nice punchline to that joke, because by solving naming in this particular way, it makes cache invalidation disappear.

Think about what makes caching hard. A cache keeps a copy of something so it can answer quickly next time. The hard question is always, when is my copy out of date? But a C-I-D can't go out of date. If it named these bytes yesterday, it names exactly these bytes today, and forever.

So a server can tell every cache along the way to keep it. The two fifty-six tee FAQ suggests a header like this one. Public, meaning any cache may store it. A max age of one year, which is the conventional way of saying "as long as you like." And immutable, which tells browsers not to even bother checking back. The C-I-D also makes a perfect version tag, since it already changes exactly when the content changes.

Two small cautions. A "not found" response is different. It's a statement about one server at one moment, not about the content, which might be published there tomorrow. So "not found" deserves a short cache lifetime, not a permanent one. And headers like the content type aren't part of the name. The same bytes have the same C-I-D whether a server calls them an image or plain text. Treat that kind of information as a hint. The same goes for the file-type suffix that the draft two fifty-six tee link format allows on the end of a C-I-D. Verification covers the bytes, not the suffix. So anyone who can edit a link could change "read this as text" into "read this as a web page," and a careless browser might then run code hidden in that text. Give those hints the same suspicion you'd give any other unverified header.
