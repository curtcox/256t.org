Say you've got a C-I-D, and you've found some server you've never heard of that claims to have it. You ask, and bytes start flowing back.

In the last episode, the advice was "always verify." That sounds simple, and it mostly is. But it's worth getting precise about, because there are a few small decisions that separate a check that's airtight from one that only looks airtight. And once verification is solid, it unlocks something very nice: permission to cache forever.

Here's the whole procedure. You requested a C-I-D. You receive some bytes. You compute the C-I-D of those bytes, using exactly the same recipe as everyone else. And you compare the two C-I-Ds as strings. If they're identical, you accept the bytes. If not, you throw them away, and try somewhere else.

Notice what's not in this loop. Nothing the server says about itself. Not its name, not its reputation, not any headers or labels it attaches. The only thing that crosses from the untrusted side to the trusted side is the bytes, and the bytes are checked against the name you already had. That's why you can fetch from a stranger.

This is where that eight-character length prefix pulls its weight.

Before a single byte arrives, you already know exactly how many bytes the right answer contains. For the Gettysburg Address, it's fifteen hundred and eleven. So you can hash the bytes as they stream in, while counting them.

If the stream ends at exactly fifteen hundred and eleven, finish the hash and compare. If the stream ends early, it's wrong, and you know immediately. And here's the important case. If a server keeps sending past fifteen hundred and eleven bytes, it's wrong too. You can hang up on it right then. A malicious server can't make you download a gigabyte of junk, or an endless stream, in order to find out that it's lying. The most it can ever waste is the length you asked for.

Knowing the length up front helps honest transfers, too. You can set aside exactly the right amount of memory, and show an honest progress bar.

There's one limit worth being upfront about. For hashed content, the fingerprint covers the whole file, so you can't be certain the bytes are right until you've seen the last one. You can reject early, but you can only accept at the end. Some other systems make a different trade-off there, and we'll look at that in the final episode.

And for small content, the story is even simpler. If the length is sixty-four bytes or less, there's nothing to fetch. The content is in the name. You don't need a server, you don't need a network, and there is nothing to trust.

Well, almost nothing. There's one subtle trap here, and it's a good one.

Remember how the single byte A became Q Q? The first Q carries six real bits. The second carries the last two real bits, plus four padding zeros. A decoder only needs those two real bits, so many decoders simply ignore the padding.

Which means if someone hands you Q R instead of Q Q, a lenient decoder will throw away those extra bits and still give you the letter A. In fact, any of sixteen different second characters will decode to the same byte. But only one of those strings, with zeros in the padding, is the C-I-D of A.

There's a second version of this trap. A C-I-D's length prefix might claim five bytes, while the characters after it only decode to two. A sloppy decoder might just return the two bytes and never notice the disagreement.

Now, in both cases you do get the right bytes for whatever the string decodes to. The danger is in what you conclude. Two different-looking names for the same content can break anything that uses C-I-Ds as keys, like a cache, a database index, or a list of approved documents. And a name that disagrees with itself should never be accepted as a name.

The fix is the same rule as before, applied consistently. Never verify by decoding a C-I-D and trusting what comes out. Always go the other way: take the bytes, compute their C-I-D with the standard recipe, and compare the strings. The recipe only ever produces one canonical name, so anything else fails the comparison.

There's an old joke in programming that there are only two hard things: cache invalidation, and naming things. Content addressing is a nice punchline to that joke, because by solving naming in this particular way, it makes cache invalidation disappear.

Think about what makes caching hard. A cache keeps a copy of something so it can answer quickly next time. The hard question is always, when is my copy out of date? But a C-I-D can't go out of date. If it named these bytes yesterday, it names exactly these bytes today, and forever.

So a server can tell every cache along the way to keep it. The two fifty-six tee FAQ suggests a header like this one. Public, meaning any cache may store it. A max age of one year, which is the conventional way of saying "as long as you like." And immutable, which tells browsers not to even bother checking back. The C-I-D also makes a perfect version tag, since it already changes exactly when the content changes.

Two small cautions. A "not found" response is different. It's a statement about one server at one moment, not about the content, which might be published there tomorrow. So "not found" deserves a short cache lifetime, not a permanent one. And headers like the content type aren't part of the name. The same bytes have the same C-I-D whether a server calls them an image or plain text. Treat that kind of information as a hint.

Let's go back to that honest list from the first episode. The three things the spec says are "true enough despite being false."

Verification changes what kind of statements those are. "A C-I-D uniquely determines content" stops being a claim about the universe, and becomes a rule about you: you only accept content that has this C-I-D. "The content is immutable" becomes: anything else served under this name gets rejected. And "cache it forever" becomes: once a copy has been verified, it never needs checking again.

Engineering is full of statements like this. Computers treat floating-point numbers as if they were real numbers. Networks treat a stream of unreliable packets as a reliable connection. A carpenter treats the Earth as flat. None of these are true. All of them are true enough, as long as you know exactly where the crack is, and you've decided it's somewhere you can live with. Over the last two episodes, we've measured exactly where two fifty-six tee's crack is.

So here's the payoff. Once your code verifies every C-I-D it receives, it stops mattering who hands you the bytes. A big data center, a library, a friend's phone, a stranger's mirror. The trust lives in the name you started with, and the math that checks it.
