Bytes are arriving from a server you've never heard of. Here's exactly what your code should do, why the length in the name lets you hang up on a lying server early, and why verified content can be cached forever.

The verification loop is short: request a CID, receive bytes, compute their CID, compare the strings. Nothing the server says about itself crosses into the trusted side. The 8-character length prefix earns its keep here: a server that sends too many bytes is wrong the moment it passes the length, so it can never make you download an endless stream. Small content needs no server at all.

Then the subtle trap: decoding a CID is not verifying it. A lenient decoder turns "QR" into the same byte as "QQ", so always recompute the CID from the bytes. We cover caching forever (Cache-Control: public, max-age=31536000, immutable), why "not found" and content types are only hints, and how verification turns "true enough despite being false" into rules you enforce.
